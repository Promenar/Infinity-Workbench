# Nexara v0.2-beta 初版发行整改设计

> 日期：2026-07-12  
> 发行渠道：GitHub Release 可侧载 APK  
> 目标版本：`v0.2-beta`  
> 状态：设计已获用户确认，待实施计划拆解

## 1. 目标

把当前“可构建、可演示”的 Nexara 收敛为可供初版用户实际安装使用的 GitHub 侧载版本。发行结论必须由安全、数据完整性、核心业务闭环、后台持续生成、UI 自动化、视觉回归和签名 APK 实机验收共同证明，不能用页面数量或编译成功替代交付证据。

## 2. 已确认的产品边界

- 不兼容 `v0.1-beta` 用户数据；`v0.2-beta` 采用全新数据基线，并在发行说明中要求卸载旧版后安装。
- `minSdk = 31`，`compileSdk = 36`，`targetSdk = 36`；不追 Android 17/API 37 测试版。
- 云端 BYOK、RAG/KG、Agent 工具、工作区、备份和后台持续生成属于发行范围。
- GGUF 本地推理不继续推进，不进入稳定能力承诺；发行入口隐藏或明确标记实验性且默认不可用。
- 后台生成只覆盖用户在前台发起的当前生成任务：切后台、锁屏、旋转或 Activity 重建后继续；不支持设备重启续传、无人值守队列和定时任务。
- 初版明确支持简体中文和英文；当前深色视觉作为唯一正式主题，不保留无效的主题选择承诺。
- 所有发行 UI 入口必须是真功能；不能闭环的入口必须隐藏、移除或明确标记不可用。

## 3. 总体实施策略

采用“分阶段释放门禁”，不做跨全仓库的大爆炸式修改：

1. 安全数据基线：密钥、数据库、网络、日志、备份。
2. 核心业务闭环：Provider、审批、工作区、RAG/KG、分享导入。
3. 发行体验：首次引导、双语、错误恢复、后台生成、自适应和无障碍。
4. 发布工程：测试、Lint、CI、性能、签名、文档和 GitHub Release。

每阶段必须用 TDD 实施，产生独立可审阅提交；上一阶段门禁未通过时不得把下一阶段状态描述为完成。

## 4. 生成任务与后台服务架构

### 4.1 单一任务源

新增应用级 `GenerationCoordinator`，按 `sessionId` 管理唯一生成任务、状态流、取消和完成回调。`ChatViewModel` 只负责提交请求、观察状态和渲染，不再独占协程生命周期。`GenerationService` 与 UI 观察同一状态源，不复制请求和消息状态。

### 4.2 并发规则

- 每个会话同时最多一个生成任务。
- 初版全局最多一个活动生成任务，避免多 Provider 重复费用、通知竞争和数据库写入竞态。
- 重复提交同一请求必须返回已有任务，不得创建第二个网络请求。

### 4.3 前台服务

- 用户在可见界面点击发送时，通过 `startForegroundService()` 启动服务。
- Manifest 声明 `dataSync` 类型及对应权限。
- 服务立即发布低打扰但持续可见的通知，显示会话名、生成阶段和已生成字符数。
- 通知提供“返回会话”和“停止生成”操作；停止必须取消底层 Flow、关闭网络响应、更新消息状态并停止服务。
- 生成完成、失败、取消或系统超时时调用 `stopForeground()` 与 `stopSelf()`。
- 通知权限被拒绝时，发送前说明影响，并允许用户选择仅前台生成。
- 不从 `BOOT_COMPLETED` 或后台隐式事件启动服务。

## 5. Provider 与核心业务数据流

### 5.1 Provider 解析

- 模型持久化记录必须包含稳定的 `providerId`。
- 每次请求开始时执行 `modelId -> providerId -> ProviderConfig -> protocol/client` 解析。
- 不再用固定主 Provider 构造全局 `UnifiedLlmClient`。
- Provider 缺失、Key 缺失、模型不属于 Provider 或协议不匹配时，在发送网络请求前阻断，并提供跳转到对应配置页的恢复入口。

### 5.2 工具审批与幂等

- 审批回调直接传递本次获批的 `toolCallId` 集合。
- 新增工具执行账本，以 `sessionId + assistantMessageId + toolCallId` 唯一标识执行状态。
- 同一调用最多执行一次；Activity 重建、重复流片段、重复批准均不得重复产生副作用。
- 拒绝、取消、超时和失败形成明确终态，并作为 TOOL 消息回传给模型和 UI。

### 5.3 工作区和文件安全

- 每个 Session 创建真实 Room 根节点，并持久化 root UUID 与物理根路径。
- 资源管理器和文件工具必须以当前 Session root 为作用域。
- 补齐创建文件/目录、SAF 导入、读取、原子写入、版本快照、回收站和恢复。
- 所有路径先规范化，再验证仍位于 Session root 内；拒绝 `..`、绝对路径、软链接逃逸和跨会话 UUID。
- 写入使用同目录临时文件、同步落盘和原子 rename；数据库只在物理写入成功后更新。

### 5.4 RAG/KG 一致性

- 文件导入、写入、patch、恢复和删除发布统一索引生命周期事件。
- 重索引先隔离构建新向量，成功后事务替换旧向量与相关 KG；失败时保持旧索引可识别并提示重试。
- 删除文件必须清理向量、FTS、KG edge、孤儿 node、tag 关联和任务记录。
- JIT 微图的 nodes/edges 转换为可持久化 `kgPaths`，聊天详情页只展示真实生成的数据。

### 5.5 分享导入

- `SEND`/`SEND_MULTIPLE` 对支持的 MIME 执行真实导入并展示逐项结果。
- 不支持或读取失败的文件明确拒绝，不显示虚假的“正在导入”。

## 6. 密钥与隐私

### 6.1 SecretStore

- 不使用已废弃的 `EncryptedSharedPreferences`。
- Android Keystore 生成不可导出的 AES-256-GCM 密钥。
- 普通 SharedPreferences 只保存格式版本、随机 IV 和密文。
- Provider API Key、Tavily Key、WebDAV 密码、Vertex 私钥内容统一通过 `SecretStore`。
- UI 默认显示 `****`；眼睛按钮只在当前页面临时显示完整值，离开页面后自动重新隐藏。

### 6.2 日志和系统备份

- 关闭 Android Auto Backup，排除数据库、密钥、日志和缓存。
- Release 不落盘 Prompt、模型输出、Authorization、API Key、SQL 参数或完整堆栈。
- Debug 网络日志也必须脱敏 Authorization、Cookie 和已知密钥字段。

### 6.3 网络策略

- 所有云端 Provider 请求只允许 HTTPS。
- WebDAV 必须使用 HTTPS。
- `v0.2-beta` 不提供明文 HTTP Provider 入口；本地局域网 HTTP 端点留待后续以独立安全设计恢复。

## 7. 数据库与备份

### 7.1 数据库基线

- `v0.2-beta` 使用新的 `nexara_v2.db` 文件和 schema v1 基线。
- 启用 Room schema export 并把 schema 文件纳入版本控制。
- 删除 `fallbackToDestructiveMigration()`。
- 后续每个 schema 版本必须有连续 Migration 和升级测试。

### 7.2 备份格式

备份包头包含：

- `formatVersion`
- `databaseSchemaVersion`
- 创建时间和应用版本
- 内容清单
- 每个内容项的 SHA-256
- 是否包含密钥、是否加密及 KDF 参数

备份覆盖会话、消息、Agent、知识库真实文件、标签、任务、工作区元数据，以及 Provider 非敏感元数据、语言、RAG 配置、搜索配置和 UI 偏好。向量与 KG 属于可重建派生数据，不进入备份。

### 7.3 可选密钥备份

- 默认不包含任何 Key 或密码。
- 用户显式启用“包含完整密钥”时，必须设置备份密码。
- PBKDF2-HMAC-SHA256 使用 16-byte 随机 salt、600,000 次迭代派生 AES-256-GCM 密钥；每个备份使用独立 12-byte 随机 IV。
- 自动备份所需的备份密码仅存于本机 `SecretStore`；新设备恢复必须重新输入。
- 错误密码、认证标签错误或内容校验失败必须在写数据库前终止。

### 7.4 恢复与 WebDAV

- 下载和上传全程处理原始字节，不经过字符串转换。
- 恢复先完成读取、解密、校验、解压和解析，再在单个 Room 事务中写入。
- 恢复失败必须零写入。
- WebDAV 上传先写临时文件，成功后原子 MOVE 为最终文件名；保留最近 5 份，清理失败只警告不影响本次备份成功状态。

## 8. 发行体验

### 8.1 首次引导

顺序为：语言 -> Provider -> 连接测试 -> 默认模型 -> 首个 Agent -> 首条对话。未配置模型时不能创建无反馈的聊天会话。

### 8.2 状态透明和错误恢复

- 聊天页同时显示 Provider 和模型。
- 发送前可查看本轮 RAG、联网和工具范围。
- 鉴权、模型不存在、限流、网络、超时、RAG、工具和服务错误统一映射为可理解文案。
- 每类错误至少提供一个真实恢复动作：重试、切模型或打开对应设置。

### 8.3 语言、主题、自适应和无障碍

- 简体中文和英文用户可见文案全部资源化，禁止混排硬编码。
- 初版只承诺深色主题，移除无效主题入口。
- 宽度小于 600dp 使用 Bottom Navigation；600dp 及以上使用 NavigationRail；正文最大宽度为 960dp 并水平居中。
- 横屏、大字体和显示缩放下核心操作不裁切。
- 所有操作控件具备语义标签，触控目标至少 48dp；动态生成、审批和错误通过可访问状态变化通知。

## 9. UI 与交互验收硬门禁

UI 质量不是人工扫一眼，而是三层证据共同关闭：

1. Compose E2E：首次引导、首条对话、Provider 切换、审批批准/拒绝、后台生成、通知停止/返回、文档导入/RAG、备份恢复。
2. 截图回归：欢迎页、Agent 首页、聊天空态/生成态/错误态/审批态、Provider、RAG、备份、设置；中文和英文分别建立基线。
3. 模拟器逐流程走查：至少覆盖 360dp 手机、Pixel 7、横屏、大字体 2.0x 和平板宽度。

验收检查包括：间距、裁切、文字溢出、层级、对比度、焦点、触控目标、键盘遮挡、滚动、空态、加载态、错误态、返回行为、进程/Activity 重建和减少动效。

任何关键流程出现视觉或交互缺陷，发行门禁视为失败。

## 10. 自动化测试与发布门禁

- 全量 JVM/Robolectric 测试 0 失败；非凭证测试不允许跳过。
- DuckDuckGo 单元测试使用固定 HTML fixture；真实联网测试放入显式 integration profile。
- Android Lint 0 error；warning 必须修复或以逐项理由纳入 baseline。
- 备份包含/不包含 Key 两种 round-trip、错误密码、损坏包和恢复回滚测试通过。
- 数据库新装、清数据重建和 schema identity 测试通过，不存在 destructive fallback。
- 后台生成在切后台、锁屏、旋转、Activity 重建、通知停止和通知返回场景通过。
- Release APK 中不存在明文测试密钥、Authorization 或用户内容日志。
- Debug/Release APK 均可构建；Release 签名、冷安装、冷启动和主流程通过。
- CI 强制运行单测、Lint、Compose E2E、Debug/Release 构建和制品校验。
